# Technology stack

## Decision

GlassToKey Print Studio will be implemented as a cross-platform C# desktop application.

| Area | Choice | Initial version |
| --- | --- | --- |
| Language | C# | 14 |
| Runtime | .NET | 10 LTS |
| Desktop UI | Avalonia UI | 12.1.2 |
| MVVM | CommunityToolkit.Mvvm | 8.4.2 |
| Raster/PDF drawing | SkiaSharp | 4.151.2 |
| SVG import | Svg.Skia | 5.2.3 |
| SVG export | Internal XML/SVG writer | N/A |
| JSON | System.Text.Json | .NET inbox |
| Tests | xUnit v3 | 4.0.0 |
| Test host | Microsoft.NET.Test.Sdk | 18.10.0 |

## Why C# / .NET 10

The upstream project already contains a C# core implementation of the geometry model and layout behavior. C# therefore minimizes translation risk when reproducing GlassToKey geometry. .NET 10 is the current LTS line and gives the project a stable support horizon.

C# 14 is used through the .NET 10 SDK, but the codebase should prefer straightforward language features over novelty when that improves portability and reviewability.

## Why Avalonia

The target application is primarily a desktop editor for macOS, with Windows and Linux as desirable secondary targets. Avalonia provides one C#/XAML UI codebase across those platforms and already uses a Skia rendering backend.

The application will use Avalonia for:

- windows, panels, dialogs, menus, and commands;
- the preview surface and interaction layer;
- file selection through the platform storage APIs;
- theme and accessibility integration.

Geometry calculation must not depend on Avalonia types.

## Why SkiaSharp

PDF and PNG should be generated from the same scene model. SkiaSharp provides cross-platform vector/raster drawing and PDF document output, which keeps the renderer implementation small and predictable.

The rendering project owns Skia-specific code. The core project must not reference SkiaSharp.

## SVG strategy

SVG has two roles and they are deliberately separated.

### SVG input

Svg.Skia is used to import SVG artwork supplied by the user. Imported SVG is treated as artwork, not as application geometry.

### SVG output

Exported SVG is produced directly from the Print Scene using XML. This avoids turning the document into an opaque raster or library-specific drawing and lets us preserve:

- physical dimensions;
- groups/layers;
- editable text where possible;
- rectangles and rotations;
- clipping regions;
- embedded or linked artwork policy.

## PDF strategy

PDF is generated by the Skia renderer in physical page coordinates. The scene uses millimeters and the renderer converts millimeters to PDF points only at the output boundary.

`pt = mm / 25.4 * 72`

PDF is the canonical print format. SVG is the canonical editable format.

## Dependencies we intentionally avoid for now

- Electron/Tauri: unnecessary when the rest of the implementation is already C#.
- WPF/WinUI: Windows-only.
- .NET MAUI: optimized for app/mobile scenarios rather than this desktop editor use case.
- QuestPDF: capable, but a second layout model is unnecessary for this geometry-first editor and would add licensing/policy considerations we do not need.
- heavyweight document libraries: we only need 2D drawing and PDF export.

## Version policy

Package versions are centrally managed in `Directory.Packages.props`.

Minor/patch updates may be adopted after CI passes. Major graphics-stack upgrades require an export regression check because Avalonia, SkiaSharp, HarfBuzz, and Svg.Skia can interact at runtime.
